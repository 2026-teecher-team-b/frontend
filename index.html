Enhancement · Backend

고도화 ① RAG 검색 성능 · PR #50 #51 #41

🔴 문제

  • 데이터 증가 시 모든 벡터를 순차 비교(Full Scan) → 검색 지연
  • 동일 질문도 매번 LLM 재호출 → 비용·지연 누적
  • 청크마다 임베딩 API를 개별 호출

🟢 해결

  • pgvector HNSW 인덱스 (m=16, ef_construction=64) → ANN 탐색
  • Redis Cache-Aside (TTL 1h), 키 rag:{repo}:{q_hash}
  • 임베딩 그룹 배치 호출 + Intent별 Dense+Time 재랭킹

🔵 결과

  • Full Scan 제거 → 대규모에서도 검색 속도 유지
  • 캐시 히트 시 LLM 재호출 0회 · DB I/O 감소
  • 임베딩 API 호출 횟수 절감 · 최신 문서 우선 정확도 ↑

Intent 가중치 — LATEST 50% · NEUTRAL 30% · STABLE 10% (time score)

Enhancement · Frontend

고도화 ② 대용량 3D 렌더링

🔴 문제

  • 별 수천 개의 물리·충돌 계산이 매 프레임 O(n²)
  • 메인 스레드 블로킹 → 화면 끊김

🟢 해결

  • Spatial Hash 로 O(n²) → O(n)
  • 물리 연산 Web Worker 분리 (Float32Array Zero-Copy)
  • InstancedMesh — draw call 1회로 통합

🔵 결과

  • 메인 스레드 부담 ↓ → 끊김 없는 60fps 탐색
  • 수천 개 별 동시 렌더링 안정화
Retrospective

회고 · 배운 점

🔍 벡터 검색은 파라미터 싸움

  • HNSW의 m · ef_construction · ef_search가 recall ↔ 지연·메모리를 직접 결정
  • 인덱스 빌드 비용이 커, 대량 적재 후 일괄 생성이 유리했다

♻️ 캐시는 무효화가 본질

  • Cache-Aside 도입은 쉬워도 레포 갱신 시 stale 응답 차단이 어려움
  • TTL만으론 최신성 보장 불가 → 키 기반 무효화(rag:{repo}:*) 설계 필요

🧵 성능은 복잡도·스레드에서 갈린다

  • 물리 연산을 Web Worker로 분리 + Transferable로 복사 비용 0
  • 자료구조 선택(Spatial Hash, O(n²)→O(n))이 프레임 안정성을 좌우

📊 추측 대신 계측

  • Grafana(JVM Micrometer) · Lighthouse · Web Vitals로 병목을 수치화 후 개선
  • 수집 장애로 목표의 ~18%만 적재 → 배치 재시도·체크포인트의 부재를 체감
